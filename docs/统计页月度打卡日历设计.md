## 一、背景与目标

统计页「日常任务打卡」面板目前展示**今日打卡率**甜甜圈 + 三个数字（进行中任务 / 今日已打卡 / 累计打卡）。单日打卡率波动大、信息量低。目标：把甜甜圈替换为**当月打卡日历**（热力图风格），面板主指标改为**当月打卡率**，直观呈现整月坚持情况。

## 三、口径定义（核心决策）

**日历格子（日期 D，从月初到今天，含今天）**：
- 应打卡数 expected(D) = 创建日 ≤ D **且** D < 归档日（未归档则无上界）的任务数——即「D 当天该任务在岗」。**v1.12 修正**：归档当天起不再计入（原来 `归档日 ≥ D` 把归档日算成应打卡，但 `toggleCheckin` 对归档任务一律抛错，等于派了一个打不上卡的欠账）；归档日的打卡记录同样跳过，保证 checked ≤ expected
- 已打卡数 checked(D) = 在 D 天有打卡记录、且 D 当天活跃的任务数；`habit_checkins` 主键保证行存在即最终状态，多次打卡/取消不影响计数
- **创建日之前的补卡不计入** checked（也不计入 expected）：任务今天建、补昨天的卡，昨天格子保持中性。不排除的话比率会超 100%（1 个任务补 6 天卡 = 700%）
- 完成度 = checked / expected；expected = 0 的格子为中性色，不参与月比率；**未来日期**同中性且禁用态

**单日状态：三档（v1.12，由原 4 档合并）**：

| level | 状态 | 判定条件 | 说明 |
|---|---|---|---|
| 0 | 未打卡 | expected > 0 且 checked = 0 | 当天有应打卡任务，一项都没打 |
| 1 | 部分完成 | 0 < checked < expected | 打了但没打完；因为只有 1 项任务时非 0 即满，这一档**必然**发生在当天有 ≥2 项任务的日子 |
| 2 | 全部完成 | checked = expected > 0 | 当天所有应打卡任务都完成 |
| — | 无任务 | expected = 0（含未来日期） | 中性，不参与月率 |

> 原 4 档按完成度 0 / <50% / <100% / 100% 分，问题是 0% 与 <50% 底色几乎同色（`#f6f9f7` vs `#dbeee9`）、<100% 与 100% 也只差 20% 透明度，肉眼分不出四档。合并后三档只问「打没打、打全没打全」，正是用户能直觉回答的问题。

**当月打卡率（面板主指标）** = Σchecked / Σexpected，D 从月初到今天、仅 expected > 0 的日子。

边界约定（逐条可复算）：
- **未来日期不进分母**：还没到的日子不算欠账。
- **今天进分母**：它是真实的应打卡义务（「到今天为止欠了多少」的口径），所以早晨看会比当晚略低，随着当天打卡逐格收起而回升。备选「今天进了分子才进分母」会造成「打了卡反而掉分」（15/15 打 1 个变 16/18），备选「今天完全不计」则打卡后主指标纹丝不动，两者都已否决。
- **创建日之前的补卡**：既不计分子也不计分母（任务还不存在的那天无从谈起），仅以 `stray` 标记让 tooltip 能解释「这天为什么没上色」。
- **月中新建 / 归档任务**：expected 按日计算，只在任务在岗的那些日子计入分母；归档当天起不再计入（见上）。
- **归档恢复**：`archived_at` 置 NULL 后归档区间会被重新计为应打卡，而超出 7 天补卡窗口的日期已经补不上，月率会永久偏低。修法需要「历史区间表」，改动面大于本次范围，**接受并记录**（见风险 5）。
- **删除任务**：打卡记录随外键级联删除，统计不残留孤儿数据（列表里也没了，口径一致）。
- **同一天重复打卡**：主键 (task_id, checkin_date) 去重，分子最多 +1。
- **Σexpected = 0**（无任务 / 本月尚无应打卡日）→ 返回 `null`，界面显示「—」并提示「本月还没有应打卡的日子」。
- **取整规则**（v1.12 新增）：0 次打卡 = 0%；已打卡 ≥ 应打卡 = 100%；其余四舍五入后**钳制在 1–99**。
  否则会出现「打过 1 次却显示 0%」（1/300 = 0.33%）和「差一格却显示 100%」（199/200 = 99.5%）两种说不通的读数。

**格子色阶（三档，v1.12）**：
| level | 颜色 | 说明 |
|---|---|---|
| 0 未打卡 | **不上色**，只留弱化日号（与「无任务」同款） | v1.12 定稿：漏卡不再用灰底 + 描边表示——满屏灰方块把真正打了卡的日子淹掉了，用户明确要求去掉那圈边框 |
| 1 部分完成 | `--primary-300` = `#79b9ad` 底，文字新变量 `--primary-800` = `#054038` | 复用既有色阶 token，不新增中间色值；中青底上白字只有 2.1:1，必须用深青字 |
| 2 全部完成 | `--primary` = `#0d6e61` 底，白字 | —— |
| — 无任务 / 未来 | 不上色，只留弱化日期 | v1.12 新增 `.no-task`，见下 |
| — 补卡留痕 | `--primary-soft` 底 + `--primary-100` 内描边 + 4px `--primary` 圆点（`.stray`） | 创建日之前的补卡，不计入月率但不吞掉 |

两档填色对白底的相对亮度 0.42 / 0.12，对比度 2.7，靠**明度台阶**而非色相区分，红绿色盲与劣质显示器下同样可分；日期字对比度 5.1:1 / 6.1:1，均过 4.5:1。

> 代价要记着：未打卡和「当天没有任务」现在视觉完全一致，漏卡在日历上看不出来（只能从「应打卡 70 次 − 已打卡 47 次」倒推）。如果以后要找回这个信号，最小改动是把漏卡日期的字色从 `--ink-400` 加深到 `--ink-600`，不加任何框。

三点配套修正：
1. **`expected = 0` 的日子不再画灰方块**。原来这些天渲染成和「未打卡」同款的浅灰块，月中新建任务时半屏灰块、日号几乎看不清，等于把「没任务」误报成「漏卡」。现在只留弱化日号（`.no-task`），和未来日期同属「不参与统计」。
2. **今天用 inset 描边而非外描边**。格子是 grid item，`outline-offset: 1px` 会压在相邻格子的边界上；改 `box-shadow: inset 0 0 0 2px`，并按档位换描边色（0 → `--primary`，1 → `--primary-800`，2 → `--primary-300`），三档下都看得见。
3. 图例只标两种填色状态（部分完成 / 全部完成 + 「未打卡与无任务的日子不上色」），每项带 title 说明判定规则；格子 tooltip 写「N 月 M 日 · 档位名（已打卡 x / y）」，今天且尚未打卡时写「今天还没打卡」而不是「未打卡」。


## 四、方案

### 4.1 主进程（main.js）
新增 IPC `habits:calendar(year?, month?)`（缺省当前月；**month 为 1-12**（非 getMonth() 的 0-11），入参按库内惯例做整数与范围校验，非法回退当前月），为探针构造边界月份与后续月导航留增量：
1. SQL 取打卡：`SELECT task_id, checkin_date FROM habit_checkins WHERE checkin_date BETWEEN 'YYYY-MM-01' AND 'YYYY-MM-31'`（字符串比较，30/31 天月与月末均正确；checkin_date 已过 validateDeadline，无非法日期，加注释说明）
2. SQL 取任务：`SELECT id, created_at, archived_at FROM habit_tasks`（全量，本地单机量级）
3. JS 逐日聚合（本地时区）：**D ∈ [当月月初, min(今天, 当月月末)]**——传参历史月份时上界收到当月月末（否则字面迭代会跨出目标月）；传参未来月份则无聚合日，全格子未来态中性、monthRate = null。活跃判定把 UTC 串转本地日期——`new Date(str.replace(' ', 'T') + 'Z')` 是标准 ISO 解析（与 renderer.js:295 既有用法同款），取本地年月日后与 checkin_date（本地日期串）比较，严格一致
4. 返回 `{ year, month, days: [{ date, checked, expected, level, stray }], monthChecked, monthExpected, monthRate, summary: { activeDays, fullDays, partialDays, missedDays }, activeTasks }`（monthRate 在 Σexpected=0 时返回 null，渲染层显示「—」；**v1.12** 新增 `summary` 与 `activeTasks`：前者恒满足 `fullDays + partialDays + missedDays === activeDays`，后者供 caption 与同一次响应同源，避免「暂无任务」与有数据同屏）
5. **v1.12**：`level` 只有 0/1/2 三档 + null（无任务日）；取整逻辑抽成 `habitMonthRate(checked, expected)` 纯函数，集中一处便于口径复核

### 4.2 preload.js
`habits` 命名空间新增 `calendar: (year, month) => ipcRenderer.invoke('habits:calendar', year, month)`。

### 4.3 渲染层（renderer.js / index.html / styles.css）
- index.html：`.donut-wrap` 整块替换为 `.habit-calendar`（周日首表头 + 7 列网格，月初/月末用相邻月日期补齐 7 列，弱化中性不参与比率与 tooltip）
- **主指标落点（v1.12 重排）**：右列为 `.habit-summary` 两段——上段 `.habit-rate` 是「本月打卡率」hero（11.5px 标签 + 右侧「10 月 1–30 日」统计区间 → 30px 大号百分比 → 5px 进度条 →「已打卡 47 次 / 应打卡 70 次」），下段 `.habit-facts` 用 1px 分隔线接 2 行明细（今日完成 1 / 3、累计打卡 57）。原「4 行 label-值 同权重」的排法把主指标和次要数字摆成一样重；现在 30px : 13px 一眼分主次，分子分母带单位摊开，百分比可自行复核
- 为什么砍掉两行：①「进行中任务 3」与 header 的「3 个任务」完全重复；②三档天数（全勤 / 部分 / 未打卡）在 150px 窄列下必然折成两行且末行只剩一个孤词，改为放进 hero 的 title，悬停可读；③「累计打卡」改为含已归档任务（终身口径），与「今日完成 / 本月打卡率」的口径边界区分开
- **布局**：`.stats-content.habit-content`（修饰类，特异性 0,2,0 高于 1000px 查询里的 `.stats-content` 0,1,0，无需在媒体查询内重复覆盖）为 `minmax(0, 1fr) 150px`。>1000px 时双列面板最窄约 350px（恰过 1000px 阈值），日历列约 135px、每格约 17px；≤1000px 时 `.stats-grid` 切单列、面板满宽，格子随容器放大到 60px 见方（方块不变形、编号不缩水，选它优于加宽死区）
- 格子字号用 `clamp(10px, 4.4cqw, 13px)` + 容器查询（`.habit-calendar-wrap { container-type: inline-size }`）跟随格子尺寸，窄列下不会溢出、宽列下不显小
- `#habitMonthRate`、caption（「2026 年 10 月 · 共 N 个任务」）、hero 明细、格子由 `renderHabitCalendar` 用同一份响应填充，避免两处异步各自为政

- 清理：全项目 grep `habitTodayRate|habits-donut|primary-80|level-3` 确认无残留

## 七、风险与权衡
1. **UTC 时间串**：created_at/archived_at 聚合时转本地日（方案已述）；跨时区 travel 场景不处理（本地单机应用）
2. **创建前补卡排除**：用户当天建任务、补昨天的卡——月率不包含这次打卡（昨天 expected=0）。产品语义：月率衡量「该做的时候做了没」，任务还不存在的那天无从谈起。图例 + tooltip 的「x / y」让口径可解释；如用户反馈困惑，备选方案是把 expected 扩展为「最近 7 天内创建的任务往前追溯到补卡窗口」，暂不做
3. **月中增删任务**：expected 按日计算，公平反映「当天该做的做了多少」；代价是聚合逻辑集中在主进程一处
4. **刷新链路与跨天**：renderStats 的触发源比打卡链路多（60s tick 跨天、搜索击键），日历重拉随之频繁——本地 IPC 廉价且有请求序号防护，不做脏标记（如卡顿再加）
5. **归档恢复的历史区间**（v1.12 复核）：`habits:archive` 恢复时 `archived_at` 置 NULL，此前归档区间会重新计为应打卡，而超出 7 天补卡窗口的日期已无法补卡，月率会永久偏低（不是「误差有界」）。彻底修法是在 `habit_tasks` 之外存归档区间表，本次不做，**接受并明确记录**；归档恢复是低频操作，且用户可再次归档让区间退出生效范围
6. **异步渲染竞态**：请求序号防护；响应同时填充月率与日历，单一数据源
